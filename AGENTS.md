# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Agent instruction files

`CLAUDE.md` and `AGENTS.md` are kept **byte-identical**. `CLAUDE.md` is what Claude Code reads; `AGENTS.md` is what vendor-neutral agent tools read — Codex, OpenCode, Cursor, Copilot, and whatever follows them. Two real files, deliberately not a symlink: not every tool resolves one.

**After editing either file, copy it over the other — don't repeat the edit by hand:**

```bash
cp CLAUDE.md AGENTS.md   # or the reverse, whichever you just edited
```

Retyping a change is exactly how the two drift; one reflowed line or reworded clause is enough. `diff CLAUDE.md AGENTS.md` must print nothing. If it ever does, treat it as a defect and fix it by letting one file win wholesale — never by merging them.

## What this repo is

`glimpse` is a **lightweight, git-native desktop Git client** — a slim, free GitKraken-style tool. It shows the multi-branch graph and diffs, and supports everyday write actions (stage, commit, branch, push/pull). It stays small and fast by shelling out to the user's real `git` instead of reimplementing it.

It is **not** an AI-agent-specific tool. The earlier "AI companion / Revert-AI / prompt-to-diff" framing is dropped. The differentiators are now **git-native behaviour**, a **small footprint**, and **first-class WSL support** on Windows.

> [!IMPORTANT]
> **The `README.md` and the code are the source of truth.** (The earlier `docs/ARCHITECTURE.md` spec has been removed — it had diverged from the shipped app.) The application (Tauri + Nuxt) is substantially built; the meta layer (lint, format, hooks, CI, release-please) is inherited from the `scaffold` template.

## Architecture (summary)

- **Platforms:** **Windows and Linux are both first-class** native builds. macOS also compiles in CI but is **untested** (and unsigned). CI builds on an **ubuntu + windows + macos** matrix.
- **Desktop shell:** Tauri (Rust). OS-native WebView (WebView2 on Windows, WebKitGTK on Linux) — no Chromium/Electron. Small disk + RAM footprint.
- **Frontend:** Nuxt 4 (Vue 3) SPA (`ssr: false`), Tailwind v4 + shadcn-vue (Reka UI), Pinia (persisted to `localStorage`), `@nuxtjs/i18n` (**`en-GB` default, plus `de-DE`, `es-ES`, `fr-FR`**), `@nuxtjs/color-mode` (system preference, dark fallback). App code lives in `app/` (Nuxt 4 srcDir).
- **Backend — a cargo workspace rooted at `src-tauri/`:** `crates/glimpse-core` is the engine — `git.rs` + `git/parse.rs` shell out to git and parse its porcelain, **`platform.rs::resolve()`** picks the git target per repo (this replaced the old `wsl.rs`), `changelist.rs` is the changelist model. `crates/glimpse-cli` is the headless command line: a library the GUI calls through `try_run_cli()` **and** a console binary (`glimpse-cli`). `src-tauri/src/lib.rs` — package `glimpse` — keeps the Tauri commands and the debounced FS watcher (`notify`).
- **`glimpse-core` carries no Tauri dependency, and that is a contract, not a coincidence.** It is what lets the CLI run where no desktop exists. Two things hold the line: a unit test in the crate reads its own manifest, and CI runs `cargo tree --package glimpse-core` for the transitive claim the test cannot make (#103). Anything needing an `AppHandle`, a window or an IPC command belongs in the GUI package.
- **Git engine:** shells out to the **system `git` binary**, native on every OS. `platform.rs::resolve()` is native by default; on **Windows only** a `\\wsl$` / `\\wsl.localhost` repo path is routed through the distro's git via `wsl.exe -d <distro> --cd <linux-path> --exec git`. Credentials come from the user's own git setup; glimpse stores no secrets.
- **WSL (Windows-only twist):** auto-resolve per repo (Windows path → Windows git, `\\wsl$` path → WSL git). FS watcher is best-effort over `\\wsl$`, backed by manual + on-window-focus refresh. There is no WSL on Linux/macOS — git is simply native.
- **The WSL launcher (`scripts/glimpse-wsl.sh`) tells a path from a subcommand, exactly as `claims` does.** Inside a distro the installed `glimpse` is that shell script, so it — not the binary — decides whether `glimpse cl ls` reaches the command line at all; before it did, that spelling died as `no such path: cl`. A subcommand takes the **native** route when the distro has one (`$GLIMPSE_CLI`, `/usr/local/lib/glimpse/glimpse-cli`, or a `glimpse-cli`/`glimpse` on PATH that is **not this script** — a candidate resolving to the launcher is skipped, because the Linux package installs its binary under the same name and taking it would be an endless re-exec), and otherwise is **forwarded to `glimpse.exe`**, preferring the console binary beside it. Forwarding translates **only** `-C` (and injects `-C $PWD` when the caller gave none, rather than trusting the interop layer's working directory to decide which repository answers); every other path argument is repo-root-relative on both sides and passing it through untouched is the contract, not laziness. The WSL gate guards the Windows routes only — the native one needs no WSL — and it reads `$WSL_DISTRO_NAME` before `/proc/version`. `-h`/`--help` stay the launcher's own, since a distro with neither route still has to be able to say what the command is; the bare word `help` routes. `tests/wsl_shim.rs` runs the real script under `sh` against argv-recording stubs, and its guard pins the script's `GLIMPSE_SUBCOMMANDS` list against `SUBCOMMANDS` + `ALIASES` **in both directions** — nothing about adding a subcommand to Rust touches a shell script, and a word the launcher routes but the binary does not claim would shadow a directory of that name. Forwarding also knows the command line's **value options** (`VALUE_OPTIONS`, pinned from the script in both directions by the same test file): a `-m "-C"` message is the caller's text, and scanning every word for `-C` used to read it as naming a repository and translate the word after it into a Windows path — a bug the native route never had, because it hands argv over untouched.
- **The command line ships as a Tauri sidecar, and the sidecar is a build INPUT — which is why it is not in `tauri.conf.json`.** `bundle.externalBin: ["binaries/glimpse-cli"]` makes Tauri look for `src-tauri/binaries/glimpse-cli-<host-triple>` (`.exe` **after** the triple on Windows) and fail when it is missing — and `tauri-build`'s build script resolves it on **every compile**, not only when bundling, so declaring it in the checked-in config broke a bare `cargo clippy` / `cargo test` on a clean checkout for everyone. The declaration therefore lives in **`src-tauri/tauri.sidecar.conf.json`** and is merged in with `tauri build --config` at exactly the invocations that stage the file first: `pnpm tauri:build` locally (plain `pnpm tauri build` compiles the app without one), `ci.yml`'s tauri matrix and perf-baseline (`jq` folds the fragment together with their other patches), and the release chain's tauri-action (`args: --config src-tauri/tauri.sidecar.conf.json`). **Two guards in `scripts/build-cli-sidecar.test.ts` hold that split**: the checked-in config must declare no `externalBin`, and every invocation that produces a **bundle** must carry the fragment — a `--no-bundle` compile is exempt, and `ci.yml`'s matrix opts in anyway because resolving the sidecar name on all three platforms is the only Windows evidence this repo can produce without a Windows machine. `scripts/build-cli-sidecar.ts` stages the file — it asks `rustc -vV` for the host triple (never `process.platform`, which cannot tell msvc from gnu or gnu from musl), builds `-p glimpse-cli` and stages the binary under that name; `--target <triple>` genuinely cross-builds (`cargo --target`, read back from `target/<triple>/<profile>`), while `--host` is the test seam that only says what `rustc` would have reported; `--print-plan` makes the invocation testable without a toolchain, the way `check-core-tauri-free.ts`'s `--print-command` does. Where it lands is what the launcher was already looking for: **beside `glimpse.exe`** on Windows (`console_exe`'s preferred target) and on **PATH as `glimpse-cli`** from the Linux packages (`find_native`'s PATH search). **What no packaging does yet:** push a Linux `glimpse-cli` into each WSL distro — `install_wsl_shim_into` still writes only the launcher, so a distro without its own glimpse package takes the forwarding route (#103).
- **Diff:** custom `CodeDiff.vue` + `app/utils/highlight.ts` (highlight.js) + `app/utils/wordDiff.ts` — side-by-side (default) / unified toggle, ignore-whitespace, blame, file history. _(Not `@git-diff-view/vue` — that was dropped.)_ **Graph:** SVG from structured `git log`.
- **Feature surface (built):** viewing (multi-branch graph, commit search, diffs, blame, file history); staging by **file or hunk**, discard, commit, amend, conflict resolution (ours/theirs); branches create/switch/rename/delete/merge + branch-from-commit + checkout commit; cherry-pick/revert/reset (soft/mixed/hard); tags create/delete/push; stash save/pop/apply/drop; remotes add/rename/remove; fetch/pull (incl. rebase)/push (set-upstream, `--force-with-lease`); command palette, keyboard shortcuts, multi-repo tabs, recent repos, "open in editor/terminal/file manager", built-in auto-update (Tauri updater).
- **Headless CLI:** every GUI **read** view has a subcommand — `glimpse status|diff|log|show|history|blame|branches|tags|remotes|stashes|reflog|worktrees|submodules|sparse|stats|info` — plus the working-tree **writes** `glimpse stage|unstage|discard|commit|amend` (`crates/glimpse-cli/src/write.rs`), the refs-and-metadata group `glimpse branch|tag|remote|stash|cherry-pick|revert|reset` (`crates/glimpse-cli/src/refs.rs`), the network operations `glimpse fetch|pull|push` (`network.rs`), the paused flows `glimpse rebase|bisect|resolve` (`paused.rs`), the one-shot layout writes `glimpse worktree|submodule|sparse` (`layout.rs`) and `glimpse cl ls|add|mv|rm|active|commit` (changelists), each with `--json` and `-C <dir>`, plus `glimpse --help` / `--version`. Both globals work **before** the subcommand as well as after it (`glimpse -C sub status`): `globals_after_the_subcommand` in `crates/glimpse-cli/src/lib.rs` rewrites argv so the one parser sees either spelling, and `claims` looks past them too — otherwise the single installed binary would read `-C` as a path and open a window. A subcommand counts as shipped only once it is in `SUBCOMMANDS`, `glimpse --help` **and** the README; the same two guards read `GROUPED` as well, because `branch` appearing in the help says nothing about `branch delete` and it is the _action_ #103's criterion (b) is about. Four `cargo` tests enforce it (the README guard matches on a word boundary, so a rename that keeps the old name as a prefix fails it). Every write action in #103's scope now has a subcommand, and the claim is kept **narrow on purpose**: the CLI works at file granularity, so hunk- and line-level staging, discarding and partial commit stay GUI-only, as do interactive history rewriting, the merge editor's save, patch import/export, a detached checkout and clone/init. Saying "every write action" was false and contradicted the README thirty lines further down, so the prose now names what is missing instead. **Packaging and distribution** are what remain open (#103) — shipping the Linux `glimpse-cli` into each distro, and the console binary in the Windows installer.
- **Grouped commands are a group word plus a verb**, the shape `cl` set: `glimpse branch create`, `glimpse stash drop`. The bare word still **lists** (`glimpse branch` = `glimpse branches`, `glimpse stash` = `glimpse stashes`, and `tag`/`remote` gained `tags`/`remotes` to list into) — `listing_instead` in `write.rs` routes that back to `read.rs`, so there is one renderer per subject rather than two. `branch` and `stash` used to be read-only aliases; the bare spelling means exactly what it always did.
- **Everything destructive states its confirmation, and the rule is one rule.** Naming the subject **is** the confirmation — `discard <file>`, `branch delete <name>`, `stash drop <stash>` need no flag, which is why `stash drop` refuses to assume `stash@{0}` the way bare `git stash drop` does. An action naming **no** subject carries `--force`: `discard --all --force`, and `reset --hard` **only when something is at risk** — decided against the **target tree**, not `status`: a tracked or staged change always is, an untracked path only where the target tree **needs its name** (`Repo::paths_in_tree`), which is three relations and not one — the target holds a file at the path, at any **ancestor** of it (so the directory holding it is replaced), or anywhere **under** it (so the file is removed to make room for a directory). Asking only about the exact path is what let a checkout silently delete untracked work whose name collided by shape. Warning about an untracked-only tree it would not touch is equally wrong in the other direction — false, and the fastest way to teach `--force` as a reflex. `branch delete --force` is the one flag that means something extra — deleting the ref is what was named, losing commits no other ref holds is not, so it maps to `-D` while the plain form stays `-d`.
- **A verb that _begins_ an operation refuses while one is open** (`refs::in_progress` → `MERGE_HEAD` / `CHERRY_PICK_HEAD` / `REVERT_HEAD`): `branch merge`, `cherry-pick`, `revert`, and `discard --all --force` all ask first, so the refusal lands before anything is touched and names the paths still in dispute. A paused rebase is in that set too, now that `glimpse rebase continue|skip|abort` exists to finish one — and it is asked of the sequencer's **state directory** (via git, never `Path::exists`) rather than of `REBASE_HEAD`, because that ref is set only when the rebase stops _on a commit_: a `break` and a failed `exec` are just as paused and set nothing. `reset --hard` is likewise not refused: it _clears_ those refs, so it concludes the operation instead of hiding it, and it is currently the only route out of a stopped one.
- **The refs commands read their outcome back from the ref store**, the way the working-tree ones read theirs back from `status`: `current_branch`, `branch_names`, `tag_names`, `remote_names`, `commits_since` and `remote_url` on `Repo` exist for exactly that, and are cheap probes rather than `info()`, which runs half a dozen git commands to answer one question. A cherry-pick or revert writes **new** commits, so the report carries the hashes git actually wrote, never the ones it was handed; `push_tags` uses `--porcelain` because the human format goes to stderr, which the engine returns only on failure (a successful `git push --tags` used to hand its caller an empty string), and it returns a `TagPush` rather than a `Result` because a push is a **batch** — one rejected tag exits 1 with the others already pushed, and a `?` would throw away the only record of them (`Repo::run_capturing` is the seam that keeps stdout whichever way git exited).
- **Every CLI path argument is repo-root-relative**, on every command — the spelling `glimpse status` prints, `--json` reports back and the changelist store records. `open_repo` in `crates/glimpse-cli/src/lib.rs` is the single seam that enforces it: it re-anchors the `Repo` at `rev-parse --show-toplevel`, so a command cannot opt out by forgetting to. Bare git pathspecs are cwd-relative; the CLI deliberately is not, because its output is what feeds its own input. **Two arguments are outside the rule and the rule's own statement now says so**: `-C <dir>`, which picks the repository rather than living in it, and the `paths` a `worktree add|remove` reports — a linked worktree usually sits outside the root, so git's absolute path is the only honest spelling and a `../../..` chain would not be one. A contract stated without its exceptions is worse than one stated with them: a script written against it gets a different shape from two verbs with nothing warning it.
- **`discard` is the only CLI command that destroys work, and it is built to refuse.** It goes to **HEAD**, index included (`Repo::discard_to_head`) — a staged change is uncommitted work, so `git restore <file>`'s index-sourced semantics would leave it behind while the report claimed otherwise. The GUI's per-file button keeps those index-sourced semantics (`Repo::discard`) because it lives in the _unstaged_ section, and the two methods are separate for exactly that reason. The plan is resolved against `status` first and refuses there what git cannot discard per path (an unresolved conflict, a staged rename); the destruction is one `git restore` plus one `git clean` for the whole batch; and the outcome is **read back from `status`** rather than assumed, so a path git silently declines fails the command instead of being reported as gone. `--all --force` carries the same read-back, and snapshots the tree **before** destroying anything — without that snapshot it has no path names for the already-destroyed half and reports "Nothing was discarded" after wiping the tree. It also **refuses outright while a merge, cherry-pick or revert is in progress** (`refs::in_progress`, i.e. `MERGE_HEAD` / `CHERRY_PICK_HEAD` / `REVERT_HEAD` set, conflicts resolved or not): `--force` is consent to lose the working tree, not to settle a conflict on _ours_ and leave the operation open behind a clean-looking `status`.
- **A headless write notifies a running window, best-effort.** After a successful write the CLI drops a receipt at `<git-dir>/glimpse/last-write.json` (`Repo::write_receipt`, beside the changelist store) and the GUI watches that one file with a 50ms debounce — far faster than the recursive watcher's 400ms, and than its multi-second poll over `\\wsl$`. Both halves are best-effort by design: **a failed notification must never fail the write that succeeded**, matching the posture the FS watcher, the WSL shim install and the PATH install already take. The dispatcher in `write.rs` sends it in one place, so a new write command inherits it like it inherits `--json` and `-C`.

## Dev & testing on WSL

This repo is often developed inside WSL2. Practical loop:

- **Frontend demo:** `pnpm dev` (Nuxt) runs in WSL; open `http://localhost:3210` from the Windows browser. Fastest UI iteration. Backend IPC is mocked when not running under Tauri.
- **Full Tauri shell in WSL:** needs `rustup` + `webkit2gtk-4.1` + build deps; produces a **Linux** build shown via WSLg. Not the Windows target.
- **WSL-git feature + Windows behaviour:** can only be exercised in a **Windows** build (that's where `wsl.exe` is invoked). Build/run on Windows for those.

## Meta-layer conventions

- **Node 24, pnpm 11.** Pinned via `.nvmrc`, `engines`, and `packageManager`. `pnpm-workspace.yaml` enforces `minimumReleaseAge=4320` (3-day cooldown), isolated node-linker. Don't loosen these without reason.
- **Types are checked, and the gate is where.** `pnpm typecheck` sits inside `pnpm check` and runs `vue-tsc` **three** times, because no single tsconfig covers the repo: `nuxt typecheck` for the app (`.vue` files included), `-p tests/e2e/tsconfig.json` for the WebdriverIO suite, and `-p tsconfig.tooling.json` for the Node-side tooling (`vitest.config.ts`, `build/**`, `scripts/**`). They stay separate because their `types` sets are mutually exclusive — Vitest against `mocha` + `@wdio/globals` — and merging them would let each suite type-check the other's globals. A `ts-rs` binding that gains a required field therefore fails locally instead of shipping. `vue-tsc` rides TypeScript 6 through volar's shim fallback in `runTsc` — TS 6 moved the compiler to `lib/_tsc.js` and left `lib/tsc.js` as a loader shim — so keep an eye on that path when either is upgraded.
- **oxc, not eslint/prettier.** Linting via `oxlint`, formatting via `oxfmt`. Configs live in `.oxlintrc.json` / `.oxfmtrc.json`. `oxlint` uses `unicorn` + `oxc` plugins; rules deliberately minimal.
- **Husky hooks** (`.husky/pre-commit`, `.husky/commit-msg`) run `lint-staged` and `commitlint`. `lint-staged.config.js`: `oxlint --fix --deny-warnings` then `oxfmt` on JS/TS; `oxfmt` on JSON/JSONC/YAML/TOML/MD (excluding `README.md` and `pnpm-lock.yaml`); `rustfmt --edition 2021` on `*.rs`.
- **Conventional Commits enforced** via `@commitlint/config-conventional`. Don't `--no-verify` unless explicitly asked.
- **release-please** drives versioning. Files: `release-please-config.json` (`release-type: node`, `include-v-in-tag: true`), `.release-please-manifest.json`, `.github/workflows/release-please.yml`. The repo starts at `0.0.0`.
- **Workflows** use `actions/checkout@v6`, `actions/setup-node@v6`, `pnpm/action-setup@v6`, `github/codeql-action/{init,analyze}@v4`. Keep these pinned to major versions; Dependabot bumps them monthly.
- **CodeQL** scans `actions` + `javascript-typescript` with `security-extended,security-and-quality` queries, gated by path filters. When Rust lands, consider extending coverage.
- **Dependabot** groups all minor/patch updates per ecosystem into a single PR. Majors come as separate PRs.

## House style for READMEs and meta files

The `/write-readme` skill encodes the canonical structure. Key rules: hero block wrapped in `<div align="center">`, prescribed section emojis (✨ Features, 🚀 Setup, 🤝 Contributing, 🛣️ Versioning, 📄 License), license footer always reads `[MIT](LICENSE) © [Titus Kirch](https://github.com/TitusKirch/) / [IT-Dienstleistungen Titus Kirch](https://kirch.dev)`. Use GitHub callouts (`> [!TIP]`, `> [!IMPORTANT]`), never plain blockquotes.
