title: Changelists
description: How pending changes are grouped, where that grouping is stored, and how it survives edits made outside glimpse.
---

A changelist is a named group of pending changes layered over one working tree.
The model is deliberately small: a list has an id, a name that doubles as its
commit message, and its members. One list — `default` — is permanent, and
brand-new changes land in whichever list is active.

## Where the grouping lives

Membership is stored as JSON in the git directory, at
`<git-dir>/glimpse/changelists.json`.

**The git directory, not the working tree**, so the grouping travels with the
clone without ever appearing as a change to be committed. And **a documented
file rather than app-private state**, so the GUI is not the only thing that can
read it: `glimpse cl` works headlessly against the same file, and so can any
other tool.

The model exists twice for that reason — `app/utils/changelist.ts` for the GUI
and `src-tauri/crates/glimpse-core/src/changelist.rs` for the CLI — with shared unit tests guarding
the two against drift. The Rust port is what lets `glimpse cl` run without a
JavaScript runtime.

## Reconcile: anyone may run git on the side

Stored membership can always be stale, because nothing stops the user
committing, stashing or discarding in a terminal while glimpse is open. So the
stored state is never trusted as-is. Reconciling it against the real set of
changed paths does three things: drop members that are no longer changed, route
changes glimpse has not seen into the active list, and leave every still-valid
assignment exactly where it was.

That last one is the point. A reconcile that reshuffled valid assignments would
undo the user's work every time git ran anywhere else.

## Hunk-level membership

::callout
**Status:** in development
::

File-level membership cannot express "these two edits in one file belong to
different commits", which is the case changelists exist for. Membership is
therefore moving down a level, so the invariant becomes _a hunk_ — not a path —
lives in exactly one list.

Two decisions carry that:

**A hunk is identified by a hash over git's `@@` caption and the body, with the
line numbers left out.** Line numbers shift whenever anything above a hunk
changes, so an identity that included them would be lost on the first unrelated
edit.

**Drift is resolved in two stages and never silently.** An exact hash match
first; on a miss, the added and removed line contents are overlapped against
what was stored. A hunk that resolves by neither is treated exactly like a
brand-new change — it goes to the active list, never to some list it was not in
— and its file is reported so the interface can mark it.

The on-disk change is **additive and stays at schema version 1**. Both readers
reject an unknown version and then write version 1 back, so raising it would
make an older build, or an older `glimpse cl`, _delete_ a split rather than
ignore it. Keeping the file-level `members` field populated means an older
build degrades to whole-file membership instead.
