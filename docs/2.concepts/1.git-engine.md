title: The git engine
description: Why glimpse shells out to the user's own git, and how it decides which git that is.
---

glimpse runs the `git` binary already on the machine instead of linking a git
implementation of its own. Every read and every write goes out as a command
line and comes back as text glimpse parses — the porcelain formats in
`src-tauri/crates/glimpse-core/src/git/parse.rs`.

## Why shell out rather than link a library

Linking libgit2 or gitoxide would remove the parsing layer, and it was still
the wrong trade for this program.

**The user's git is the one their repository already works with.** Credential
helpers, `~/.gitconfig`, hooks, `core.fsmonitor`, LFS, signing keys, a
company's `insteadOf` rewrite — all of it applies because the same binary runs.
A linked library reimplements that surface one feature at a time, and each gap
is a repository that behaves differently in glimpse than in the terminal.

**It keeps glimpse out of the credential business.** Authentication is the
user's git's problem, which is why glimpse stores no secrets at all.

**It keeps the binary small**, which is one of the project's stated
constraints.

What it costs is real and worth naming: output has to be parsed, and porcelain
output is a contract only where a `-z` or `--porcelain` flag says it is. That
parsing is the part covered by Rust unit tests, because it is the part that
breaks silently.

## How the target git is chosen

Everything above `GitTarget` is platform-independent; `platform.rs::resolve()`
is the single place that decides what a `GitTarget` actually points at.

The order is fixed:

1. **An explicit `glimpse.target` git-config value wins.** Any scope is read,
   repo-local first, so a single repository can be pinned without touching a
   global setting.
2. **Otherwise the path decides**, and only on Windows: a working copy under
   `\\wsl$` or `\\wsl.localhost` is routed through that distribution's own git
   (`wsl.exe -d <distro> --cd <linux-path> --exec git`). Everything else is
   native.

There is no WSL interop on Linux or macOS, so `resolve()` is native there by
construction rather than by a branch that happens not to be taken.

**Routing by path rather than asking the user** is the decision worth knowing.
A repository living inside a WSL distribution has Linux file modes, Linux line
endings and a Linux `.git` — driving it with Windows git produces a working
copy that looks modified to the distribution's own git and vice versa. The path
is the evidence, so the path decides, and `glimpse.target` exists for the cases
where evidence and intent differ.

The cost is that the filesystem watcher is best-effort across the `\\wsl$`
boundary, so a WSL repository also refreshes manually and when the window
regains focus.
