glimpse ships through three channels, and only the first one is what a user
gets by default.

| Channel    | Trigger                            | Builds                           | Release                                                     |
| :--------- | :--------------------------------- | :------------------------------- | :---------------------------------------------------------- |
| Stable     | a release-please release on `main` | Windows + Linux                  | the versioned `vX.Y.Z` release                              |
| Beta       | manual dispatch                    | Windows + Linux + macOS          | a `vX.Y.Z-beta.N` prerelease, plus a rolling `beta` release |
| Experiment | manual dispatch, per branch        | the subset the dispatch asks for | a rolling `experiment-<slug>` prerelease                    |

macOS compiles in CI but is untested and unsigned, so stable does not offer it
as a download.

## How a stable release is cut

release-please owns the version. It opens a release pull request against
`main`; merging that request is what tags the release, writes the changelog and
publishes the release page. Only then does the installer build run, uploading
the artifacts onto the release that already exists.

**The build never creates the release, and this matters more than it looks.**
It uploads onto a release addressed by its numeric id rather than by its tag.
Handed a tag, `tauri-action` looks the release up itself and then overwrites
the name and body of whatever it finds with its own inputs — which, with no
release body configured, silently empties the changelog release-please just
wrote. Addressing by id skips that path entirely.

## What the updater depends on

The updater points at
`releases/latest/download/latest.json`, which GitHub resolves to the newest
**stable** release — prereleases are skipped by that alias, which is why the
beta channel keeps a separate rolling `beta` release holding only its own
manifest.

Two consequences follow, and both have bitten this repository:

- **A stable release with no `latest.json` breaks updates for everyone already
  on a stable build**, not just for new installs.
- **The manifest is assembled once**, after the platform builds finish, rather
  than by each build in parallel. Parallel writers all target the same file, so
  the last writer wins and the other platform disappears from the manifest.

Signing keys for the updater are fetched at build time rather than kept as
repository secrets.

## Repairing a release

The stable build can be dispatched manually against a tag that already shipped,
which rebuilds its installers from the tag itself rather than from the current
branch — so the binaries match what the release page says they are. It refuses
a tag that has no release, rather than creating one.

## Checklist

- [ ] The release pull request is merged into `main`, so the tag and changelog exist
- [ ] The installer build ran and its artifacts are attached to that release
- [ ] `latest.json` is attached and names both Windows and Linux
- [ ] The release page still shows its changelog after the build finished
